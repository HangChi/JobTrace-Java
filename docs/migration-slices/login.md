# Compatible Account Login (Feature 020)

This slice adds only anonymous `POST /api/auth/login`. The route preserves the registration-era same-origin guard, applies a separate ten-attempt-per-minute `login` source limit, and calls the optional challenge verifier before credential lookup. An absent Origin is allowed for non-browser clients; an explicit cross-site or mismatched Origin is rejected. Forwarded client-address headers are not trusted by default.

Login accepts `identifier` or the legacy `username` alias, verifies a Better Auth-compatible scrypt credential, and resolves email only against verified recovery addresses. Unknown, wrong-password, unverified-email and disabled accounts return the same `invalid_credentials` response without creating a session. A successful login inserts one seven-day row in the existing `sessions` table and emits a Better Auth HMAC-signed, HttpOnly, SameSite=Lax cookie. HTTPS/explicit secure-cookie configuration adds `__Secure-` and `Secure`. The JSON body contains only a safe local `redirectTarget`; it never exposes the session token. Responses are non-cacheable and diagnostics use only bounded outcomes.

The Java endpoint needs `BETTER_AUTH_SECRET` to match the old service. `BETTER_AUTH_URL=https://...` enables secure cookies, and `JOBTRACE_AUTH_SECURE_COOKIES=true` can force them behind an HTTPS-terminating proxy. Missing signing configuration fails closed before session creation. The old service continues to own production routing and accepts these shared sessions. Java protected routes still require signed bridge assertions, not the browser cookie. A future rollback routes only this POST to the old service. Frontend, schema, deployment and CI/CD remain unchanged.
